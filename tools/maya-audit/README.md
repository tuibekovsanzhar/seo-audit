# Maya Audit 0.2.8 — standalone tool

This is the Maya Audit Python package, including the technical SEO check `TSEO-1`, crawler, tests, fake-site test server, setup scripts, and documentation. It is intended for Maya's engineering team to review and run; it is not a dashboard or a one-click website app.

## New teammate

Requires Python 3.11+ and Git. macOS/Linux commands; on Windows use `.venv\Scripts\python.exe` and `.venv\Scripts\pip.exe`.
The tool lives in the `tools/maya-audit/` folder of the private repository `withmaya/seo-audit`; every command below
runs in that folder.

```sh
git clone https://github.com/withmaya/seo-audit.git
cd seo-audit/tools/maya-audit
python3 -m venv .venv
.venv/bin/pip install -e ".[team,dev]"
.venv/bin/python -m playwright install chromium
cp .env.example .env        # then fill in only the keys you use; never commit .env
.venv/bin/python -m maya_audit_web
```

Open http://localhost:8770. To try it without any keys or live requests, start `.venv/bin/python -m maya_audit_web --demo`
instead (a made-up site, nothing is sent anywhere).

To update: `git pull` (in `seo-audit/tools/maya-audit`), then stop the app (Ctrl+C in its terminal) and start it again with
`.venv/bin/python -m maya_audit_web`. If `pyproject.toml` changed, run `.venv/bin/pip install -e ".[team,dev]"` first.

Your audits, reports and spending ledgers live in `~/.maya-audit` on your own computer, never in the repository. The
real-site benchmark corpus is kept outside the repository too; see `scripts/real_sites_benchmark.py` and
`MAYA_AUDIT_BENCHMARK_DIR` in `.env.example`.

## Start

Requires Python 3.11+. From this folder:

```sh
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m playwright install chromium
.venv/bin/python -m maya_audit crawl https://example.com/ --max-pages 50 --delay 2 --json reports/example.json
```

On Windows the interpreter is `.venv\Scripts\python.exe` and pip is `.venv\Scripts\pip.exe`; create the
environment with `py -3.12 -m venv .venv` (or any Python 3.11+). Every `.venv/bin/...` command in this file works with
that substitution.

The crawl prints a detailed text report in the terminal. Use `--json` for structured evidence and `--markdown` for a readable summary generated from the same findings. For example:

```sh
.venv/bin/python -m maya_audit crawl https://example.com/ --max-pages 50 --delay 2 \
  --json reports/example.json --markdown reports/example.md
```

Before making requests, the CLI checks that requested report paths do not already exist (unless `--overwrite` is set) and that output paths do not collide. Parent folders are created as needed. The readable Markdown report prioritizes suggested fixes and discloses unchecked pages and checks. Fresh reports from the three prior live runs are in the separate `Maya-Audit-Live-Reports-2026-09-28.zip`; they are examples and not generated by this update.

Only crawl sites you own or are authorized to check. The tool identifies itself, checks `robots.txt` first, obeys its rules, blocks non-public network destinations, and reports incomplete coverage as partial/not assessed. `--time-limit` bounds the crawl and data-collection phases; requests that cannot start before the deadline are skipped and excluded from INT-4. Robots.txt re-sampling is scaled to leave at least 75% of the configured time budget for other checks. Rendering requires Playwright/Chromium; if the browser cannot launch, the report says rendered checks were not assessed. Chromium's native host resolver is disabled during rendering to prevent WebSockets from bypassing Maya's HTTP proxy. Search Console, Bing, PageSpeed, access logs, and citation data are optional and require their corresponding credentials/data.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | The audit completed: the crawl ran out of pages to fetch and every check ran. |
| `3` | The audit finished but is **incomplete**: it stopped at `--max-pages` or `--time-limit`, or left discovered URLs unfetched. The reports are written and valid for what was fetched. |
| `1` | The audit is **degraded**: the site could not be read properly (blocked by bot protection, rate-limited, disallowed by robots.txt, a crawl error, or a data collector that failed). |
| `2` | Error or refused target: bad arguments, an output file that already exists, a host the tool will not crawl, or another audit of the same site already running. Nothing was audited. |

To audit one address only, add `--single-page`: that address is read and checked, no link or sitemap is followed, and
the report is titled "Single-page audit: <URL>" and says that other pages were not checked (DECISIONS 191). In the web
app this is the **Single page** button next to Quick 50 and Standard 500.

IDX-5 also asks every sitemap URL the crawl did not read, one light request each (at most 64 KB read, no redirect
followed): at most 200 by default, 1,000 from `--max-pages 500`, none with `--single-page`. `--sitemap-check-max N`
(0 to 1000) sets the cap; above it a sample spread over the site's sections is asked (DECISIONS 206). The default time
limit and the web plan's minutes include (delay + 0.3) seconds for each of these requests.

Links to other sites are checked by default (DECISIONS 211): each address once with a HEAD request, after that site's
robots.txt, at most 20 + pages read and 100 requests in all (70 for a 50-page audit, 20 with `--single-page`) and 25
other sites; only 404 and 410 count as broken, and anything a site refuses (403, 429, 5xx, no answer) is "could not be
checked". sameAs profile links come first. Add `--no-external-links` to ask nothing of other sites except the at most
10 sameAs profile links (`--check-external-links` is still accepted and changes nothing). The default time limit and
the web plan's minutes include these requests too. The web app's demo mode never asks other sites.

Add `--fast` for a Fast check (DECISIONS 219): 6 pages are rendered instead of 20, and at most 50 sitemap addresses,
20 llms.txt links, 10 images and 30 requests to other sites are checked (instead of 200, 50, 30 and 100). The pages
read, the robots.txt samples, ACC-4, the redirect re-checks, the page reader and paid data are unchanged; the default
time limit takes the smaller caps. Page reading is never cut to make room for the checks: when time runs short, links
to other sites give way first, then llms.txt links, the sitemap check, the performance rounds and rendering, and the
report names what was skipped. The Markdown report ends with a "Step timing" table (time, requests and waiting per step).

When a run is both degraded and incomplete it exits `1`. The same verdict is the `Result` line at the top of the text and Markdown reports. In a script, treat `0` and `3` as "reports are usable" and read the `Result` line for `3`.

### DataForSEO (optional, paid third-party data)

Off by default. Without `--dataforseo` the audit makes no DataForSEO request and its output is unchanged. With it, the audit adds one panel, **backlinks and authority**, from two paid calls about the site's registrable domain (`www.` and subdomains are stripped; `shop.marka.com.tr` is looked up as `marka.com.tr`):

| Check | Endpoint | What it reports | Upper-bound estimate |
|---|---|---|---|
| `DFS-1` Backlink profile summary | `/v3/backlinks/summary/live` | referring domains, backlinks, DataForSEO rank, spam score, broken backlinks | $0.0240 |
| `DFS-2` Top 100 referring domains | `/v3/backlinks/referring_domains/live` | the 100 highest-ranked referring domains (20 shown in text and Markdown, all 100 in JSON) | $0.0276 |

Planned total: **$0.0516 per audit**, shown before anything is sent. Both answers are cached for 7 days, so a repeat audit of the same domain inside a week costs $0. The results carry the confidence label **Estimated (third-party index)** and the status `observed`: they are measurements from DataForSEO's index, with no pass condition. A site that is not a public domain name (localhost, an IP address) is never sent to a paid endpoint.

DataForSEO sells the Backlinks API as a separate subscription. On an account without it, both calls come back refused (code 40204) at no cost and the panel reads "not assessed" with that reason.

**Credentials** come from two environment variables, `MAYA_AUDIT_DATAFORSEO_LOGIN` and `MAYA_AUDIT_DATAFORSEO_PASSWORD`, or from a `.env` file in this folder holding those two lines (`.env` is git-ignored; check with `git check-ignore .env`). A real environment variable wins over the file; `MAYA_AUDIT_ENV_FILE` points at a different file. They are never accepted on the command line and are replaced with `[redacted]` in every report, log line, ledger row, cache entry and error message.

```sh
.venv/bin/python -m maya_audit dfs balance                                # free: balance, today's spend, and the account's prices checked against Maya's estimates
.venv/bin/python -m maya_audit crawl https://example.com/ --dfs-dry-run   # show the plan and its total; sends nothing, crawls nothing
.venv/bin/python -m maya_audit crawl https://example.com/ --dataforseo    # audit plus the DataForSEO panel
```

**Cost guard.** Every request goes through one function, and it refuses to send unless all of these hold:

- the endpoint is on Maya's list of allowed endpoints (`ALLOWED_ENDPOINTS` in `maya_audit/dataforseo/pricing.py`: exactly the priced ones). Anything else is refused before it is priced, reserved or sent, and the SERP API (`/v3/serp/`) is refused whoever asks: Maya makes **0** SERP API calls, and every plan says so;
- the endpoint has a price estimator in `maya_audit/dataforseo/pricing.py`. No estimator, no request. The backlink estimates ($0.024 a request plus $0.000036 a row) are the higher of the figures in the two open-source tools this was modelled on, kept as upper bounds; on 2026-10-06 they matched one account's price list and the cost of a real audit exactly. `dfs balance` repeats that comparison on every run and prints "ABOVE MAYA'S ESTIMATE" if the account charges more;
- the audit's planned total is within the confirmation limit (default **$2.00** per audit, `MAYA_AUDIT_DATAFORSEO_CONFIRM_ABOVE_USD`; a normal audit with backlinks and search data, about $0.33, does not ask). Above it the CLI asks on the terminal, or needs `--dfs-approve-up-to USD` when there is no terminal;
- what this audit has already spent or reserved plus this estimate is within the limit for one audit (default **$5.00**, `MAYA_AUDIT_DATAFORSEO_AUDIT_CAP_USD`), whatever was approved. The request that would pass it is not sent, nor any after it; the report lists them as "not requested" and the audit itself finishes. A plan above the limit says beforehand which checks would be left out;
- today's spend plus this estimate is within the daily budget (default **$20.00**, UTC day; `MAYA_AUDIT_DATAFORSEO_DAILY_USD` in the environment or `.env`, or `--dfs-daily-budget USD`). Every call, paid or refused, is a row in the ledger.

The estimate is written to the ledger before the request and replaced with the `cost` DataForSEO reports afterwards. Paid calls are never automatically retried. Timeouts, dropped connections, and unusable responses retain a "possibly billed" reservation because the provider may have charged for them. Free calls may retry a server error at most twice.

**Ledger and cache** live outside the repository in `~/.maya-audit/` (`MAYA_AUDIT_HOME` moves them): `dataforseo-ledger.jsonl`, an append-only record of every call (time, endpoint, target domain, estimate, real cost, audit id, cache hit or miss), and `dataforseo-cache.db`. A cache hit costs nothing and is logged at $0; `--dfs-refresh` asks again. If the ledger cannot be read, paid calls stop with an error and the file is left as it is.

DataForSEO results are their own family (`DFS-…`), printed after the site checks and stored under `dataforseo` in the JSON report. A DataForSEO failure marks the failed check "not assessed" with the reason (and the panel "not assessed" when no call succeeded); it never changes a crawl-based check or the exit code. Each result states its source endpoint, the date the data was fetched and whether it was served from the cache.

To see what an audit cost, print the last rows of the ledger (this reads a local file; it sends nothing and needs no credentials):

```sh
.venv/bin/python -c "from maya_audit.dataforseo import panel; [print(c['ts'], c['audit_id'], c['endpoint'], c['target'], c['status'], 'estimate', c['estimate'], 'cost', c['cost'], 'cache', c['cache']) for c in panel.open_stores()[0].calls()[-6:]]"
```

Each paid call is one row: `estimate` is what was reserved before the request, `cost` is what DataForSEO reported. The audit id is also `dataforseo.audit_id` in the JSON report.

### Firecrawl (the page reader of every audit; paid third party)

**On whenever `MAYA_AUDIT_FIRECRAWL_API_KEY` is set.** Firecrawl then reads the pages of every audit, blocked or
not, up to the audit's page cap (at most 500). No flag and no confirmation are needed for the basic proxy; the
credits are printed in the plan, recorded in the ledger and held under a daily guard. `--no-firecrawl` switches it
off for one audit, `MAYA_AUDIT_FIRECRAWL=off` for the computer; without a key nothing changes and Maya's own
crawler reads the pages.

**Who does what.** Maya's own crawler still makes every direct request: robots.txt, the sitemap, redirects, HTTP
headers, response timing and the bot-access test. Firecrawl supplies page content, and the checks that judge
content (`STR-…`, `TSEO-1`, `IDX-8`) rest on its reading; each says "Source: Firecrawl". On a site Maya's crawler
can read too, each page keeps Maya's own status, headers and timing with Firecrawl's content, and a page Firecrawl
could not read keeps Maya's own reading. Only pages that robots.txt allows are requested; Maya's recorded robots
policy is reused (a 4xx, including a 403 challenge, means no rules; 429 means back off; 5xx or unreachable means
request nothing).

**Which pages, and how long.** On a site Maya's crawler cannot read, the reader takes pages in the crawler's own
order: the start page and the pages you marked important, the menu, then one page of each kind before a second of
any kind. If Maya could read no sitemap, the reader asks for it once it has read a first page (two requests at most,
counted in the maximum). Five unreadable answers in a row stop the reading, and the pages never asked for are
counted as unchecked. Part of the audit's time is kept for the reader: pages x (delay + 8 seconds); change the 8
with `--reader-seconds-per-page` or `MAYA_AUDIT_READER_SECONDS_PER_PAGE`. Before and after figures on made-up sites:
[docs/COVERAGE-BENCHMARK.md](docs/COVERAGE-BENCHMARK.md).

**When this computer cannot look a site up.** Maya asks the system resolver, asks it once more, and then looks the
name up through DNS over HTTPS (Cloudflare, then Google); the report's `crawl.network` says which answered. Before an
audit starts, the site and one public name are looked up: if nothing answers, the audit stops with "Network problem
on this computer (DNS lookup failed). Check VPN / iCloud Private Relay / Wi-Fi and try again.", with no report and no
spend. A lookup or connection that fails during an audit is "not checked", never a finding against the site, and
Firecrawl then reads robots.txt itself. `MAYA_AUDIT_DNS_OVER_HTTPS=off` keeps host names away from the public
resolvers.

**A site that challenges Maya's crawler.** When the pages were read through Firecrawl, the audit is not called
blocked: the outcome is COMPLETED, the counter reads "Pages read: 6 (via Firecrawl)", and `ACC-9` becomes one Info
note ("Cloudflare challenged Maya's own crawler (an unverified bot). …"). The measurement stays in that note's
evidence, and the checks that need Maya's own direct requests are listed once under what could not be checked.
A site is called blocked only when Firecrawl failed as well; the stronger proxies stay behind the owner-approval
flag and an exact confirmation.

| Setting | Default | How to change it |
|---|---|---|
| Proxy | `basic` (does not try to get past bot protection), sent on every request | `--firecrawl-proxy enhanced` or `auto`, accepted only together with `--firecrawl-owner-approved` ("the site owner has approved bypassing bot protection"), which is written in the report |
| Zero data retention | requested on every page (`MAYA_AUDIT_FIRECRAWL_ZERO_DATA_RETENTION=off` stops asking, for an account that does not have it: page content may then be stored by Firecrawl) | If Firecrawl refuses it, nothing more is sent and the report says "zero data retention not available". `--firecrawl-allow-without-zdr` proceeds without it for that one audit: page content may then be stored by Firecrawl |
| Pages per audit | the audit's page cap, at most 500 | `--firecrawl-max-pages N` (1 to 500) |
| Credits per day | 10000 (a guard against a runaway, not a budget) | `--firecrawl-daily-credits N`, or `MAYA_AUDIT_FIRECRAWL_DAILY_CREDITS` |
| Dollar price of a credit | not set: only credits are shown | `MAYA_AUDIT_FIRECRAWL_USD_PER_CREDIT=0.001` (your plan's price) in the environment or `.env` |
| Firecrawl's own cache | off (`storeInCache: false`, `maxAge: 0`) | not changeable |

Cost: 2 credits per page with zero data retention (1 without), plus one request for robots.txt when Maya could not
read it. The plan shows the maximum before anything is sent. Only a stronger proxy needs
`--firecrawl-approve-up-to CREDITS` covering it. Pages read are kept in Maya's own cache for 1 day
(`~/.maya-audit/firecrawl-cache.db`), so a repeat inside a week costs nothing; every request is a row in
`~/.maya-audit/firecrawl-ledger.jsonl`, in credits. A request is never retried automatically.

`--firecrawl-render` is a second, separate use: when the local browser cannot start, the sampled pages are rendered
through Firecrawl instead, under the same confirmation, limits and labelling.

The key is read from `MAYA_AUDIT_FIRECRAWL_API_KEY` (environment or `.env`), the same way as the DataForSEO
credentials. It is never printed, logged or written to a report.

```sh
.venv/bin/python -m maya_audit crawl https://example.com/ --firecrawl --firecrawl-dry-run             # the plan; sends and crawls nothing
.venv/bin/python -m maya_audit crawl https://example.com/                 # audit; pages read through Firecrawl when a key is set
.venv/bin/python -m maya_audit crawl https://example.com/ --no-firecrawl  # audit; Maya's own crawler reads the pages
```

What Firecrawl did is stored under `firecrawl` in the JSON report (added in schema 1.14; see `docs/REPORT-SCHEMA.md`).

When every page asked for comes back as a challenge page, an error or no document, the report says "Firecrawl basic
was also blocked" (with the proxy that was used), reading stops after three such pages, and the text explains that
the enhanced proxy is used only with the owner-approval flag. It is never switched on automatically.

**Website engine routing.** The HTML request uses `blockAds: true` and `parsers: []`. A provider 500 is reported
with its full redacted message and engines tried; it does not prove the site blocked a browser. Other known URLs
may still be read within the confirmed limits, with no automatic retry or proxy change. See
[the diagnosis and owner test](docs/FIRECRAWL-DIAGNOSIS.md) and [the content-provider contract](docs/CONTENT-PROVIDERS.md).

**Not verified against the real service.** Firecrawl was never called during development: parameter names come from
its public documentation and every test uses a stand-in. The credit prices, the exact wording of a
zero-data-retention refusal (the audit recognises it by the words "zero data retention" or "ZDR" in a 4xx answer),
and whether the `basic` proxy returns anything useful from a protected site are all to be confirmed on first real use.

### What a report says, and what it does not

Every report (schema 1.6 and later) has an `audit_status` section, and every output shows it as "What this audit covers":

- **Direct access:** how the site answered Maya's own crawler (let in, challenged, rate-limited, unknown). A page
  reader never changes this.
- **Content coverage:** how many distinct addresses were read and through whom, and whether that is every address
  found (a sample, and called one) or part of them, with the reasons.
- **Real AI crawlers:** server-log evidence, a limited user-agent probe from Maya's own network, or not measured.
  Reading a site through Firecrawl is never reported as crawlers being let in.

An audit is COMPLETED (exit 0) only when everything found was read; a reader's page cap, a stop, the time limit, a
page with no readable document or a missing key page makes it INCOMPLETE (exit 3). The audit's time limit covers
every step: nothing is sent to the site, a reader or a paid provider after it (`maya_audit/runclock.py`), and the
report gives the whole job's time beside the crawl's own. Decisions and who made them: `docs/DECISIONS.md` 131 to 145.

### Search data panels, Core Web Vitals, archives and ownership

`--dfs-search-data` adds the search data panels to the `dataforseo` section, as checks DFS-3 to DFS-12: domain
overview, ranked keywords, quick wins (positions 4 to 20), organic competitors, AI mentions (Google's AI answers,
and ChatGPT for the United States), a Lighthouse lab test of the homepage and up to two `--key-page`s, and, with
`--dfs-local-business --dfs-brand "Name"`, the Google Business Profile. `--dfs-country Turkey` sets the market
(United States when left out). Spelling does not matter: `Turkey`, `Türkiye`, `TÜRKİYE`, `TR` and `"Türkiye (TR)"`
are one country. A country that is typed and not recognised is an error that lists valid spellings, unless
`--dfs-default-market` says to use United States figures. If DataForSEO answers that the account has no credit
(its codes 40200 and 40210), no further request is sent in that run and the remaining checks say "not requested".
They follow every DataForSEO rule above: priced before anything is sent
(`--dfs-dry-run`), approved above $2, never more than $5 an audit, held under the daily budget, recorded in the
ledger, cached (7 days; 1 day for Lighthouse). About $0.29 for a new site. Endpoint names and prices are in `maya_audit/dataforseo/pricing.py`,
read from DataForSEO's documentation on 2026-10-08; `maya-audit dfs balance` compares them with the account's own.

After the panels run, `insights.apply_relevance` sorts the ranked keywords and quick wins into branded, relevant and
unrelated, by word matching against `--dfs-brand`, the domain's own label and the titles, headings and descriptions
of the pages read. The table keeps the first two (with a Relevance column); `unrelated` holds the rest. The audited
domain is taken out of its own competitor list. A brand name that is an ordinary word is said on each panel it
distorts (`dataforseo.relevance.common_word_brand`). A call that never left the computer (the address of
DataForSEO's server could not be looked up, or no connection could be made) is tried once more, then reported as a
connection problem with nothing charged; a call that was sent and got no answer is never repeated.

Core Web Vitals from the Chrome UX Report are added (`crux` in the report) when `MAYA_AUDIT_CRUX_API_KEY` is set:
one free request to Google about the site's origin. The key is never printed or written to a report.

`--archives` reads archived copies (Wayback Machine, Common Crawl) only when neither Maya's crawler nor Firecrawl
could read the site. They are a separate section (`archives`), each page labelled "archived/indexed copy, date X;
the live site may differ", and never change a check of the live site.

When nothing could read the site, the text and Markdown reports end with the steps its owner can take
(`maya_audit/allowlist.py`; the crawler is described in [docs/BOT.md](docs/BOT.md), whose contact details are still
to be confirmed). `--site-verification-token TOKEN` looks for the owner's token in a meta tag on the homepage;
`--verify-dns` also accepts it as a DNS TXT record (`maya-site-verification=TOKEN`, one lookup through a public
DNS-over-HTTPS resolver). A verified site is the only kind on which ACC-4 sends requests under other crawlers' names.

**Not verified against the real services.** None of the DataForSEO search endpoints, the Chrome UX Report, the two
archives or the DNS resolver was called during development. Their request and response shapes come from public
documentation; a response that does not fit is reported as "not assessed", never as zero.

### Real brand testing

Run these from a normal terminal in this folder (not from a sandboxed shell, or the browser cannot start). Copy `examples/brands.example.csv` to `brands.csv` and list one brand per line under the header `name,url`. Reports go under `output/`, which is git-ignored.

```sh
# 1. Free: the balance, today's spend, and the account's prices checked against Maya's estimates
.venv/bin/python -m maya_audit dfs balance

# 2. Free: what the whole batch would cost. Sends nothing, crawls nothing, writes nothing
.venv/bin/python -m maya_audit batch brands.csv --out output/batch-$(date +%F)/ --dataforseo --dfs-dry-run

# 3. The batch itself: a small page cap first
.venv/bin/python -m maya_audit batch brands.csv --out output/batch-$(date +%F)/ --dataforseo --max-pages 10

# 4. Afterwards: read output/batch-<date>/summary.md, then check what was really spent
.venv/bin/python -m maya_audit dfs balance
```

Leave out `--dataforseo` in step 3 for a batch that costs nothing. What the batch does:

- Brands run **one at a time**, each through the normal audit: the same URL safety, robots.txt handling, delay between requests, per-site lock and DataForSEO cost guard as `crawl`. `--max-pages`, `--time-limit`, `--delay`, `--no-render` and `--render-browser-channel` apply to every brand.
- **One brand failing does not stop the others.** Its row in the summary carries exit code 2 and the error text.
- Per brand it writes `<name>.json` and `<name>.md` (the name made safe for a file name), then `summary.csv` and `summary.md` with one row per brand: exit code and its meaning, duration, pages checked and redirects followed (counted separately: "10 pages + 1 redirect") and URLs discovered, rendering mode and pages rendered, findings by severity, checks not assessed, DataForSEO status, cost and whether it came from the cache, and any error.
- **Before anything is fetched** it prints the DataForSEO plan for the whole batch and stops if the total does not fit what is left of today's budget (`--dfs-daily-budget`, default $20.00). A total above the confirmation limit ($2.00 by default) needs a yes on the terminal or `--dfs-approve-up-to USD`, and no single site may spend more than $5.00 (DECISIONS 192). While the batch runs, the ledger still checks the budget before every single call.
- Existing reports in `--out` are not replaced unless `--overwrite` is given.
- Exit code of the batch: `0` every brand has a usable report (its own exit 0 or 3), `1` at least one brand failed or was degraded, `2` the batch could not start.

### Which pages a capped crawl checks

A crawl that stops at `--max-pages` is a sample, so the order matters. Maya fetches, in this order:

1. the start URL, and where it redirects to. The redirect's target is the real homepage (`http` to `https`, `example.com` to `www.example.com`, `/` to `/tr/`) and is always fetched next, even when the sitemap had already listed it. A redirect is not a page and does not use up the cap;
2. key pages (`--key-page`);
3. pages linked from the navigation (`<nav>`, `<header>`, `role="navigation"`);
4. everything else, one page per section of the site before a second page of any section. A section is the URL's path with its last part dropped (`/tr/blog-post/` and `/tr/another/` are both `/tr/*`; `/tr/services/x/` is `/tr/services/*`). Linked pages go before sitemap-only ones.

A link to another site at a path that is also a page of this site (often an internal link written with the wrong
domain) is requested once, after that site's robots.txt, at most 10 such addresses an audit; it is reported only when
it answers 404 or 410. Name the brand's other domains with `--brand-family-domain other-shop.example` (repeatable,
host names only): links to them are never reported or requested.

To audit particular sections of a large site, name them as key pages:

```sh
.venv/bin/python -m maya_audit crawl https://example.com/ --max-pages 30 \
  --key-page /tr/services/ --key-page /tr/doctors/ --json output/example.json --markdown output/example.md
```

### Time limit

`--time-limit` is for the whole audit. Left out, it is scaled to the run: 360 s for 10 pages, 660 s for 40 pages with 12 key pages, never under 300 s. A limit given by hand that is below the estimate prints a warning before the audit starts.

When the limit is reached the audit still delivers what it can:

- the crawl stops at 60% of the limit, so the checks that follow have time;
- every check that only reads the pages already fetched still runs. Links it would have requested are reported as "not checked", never as broken; rendering falls back to raw HTML;
- the report says what was lost: a "Cut short by the time limit" section at the top of the Markdown report, `Time limit` lines in the text report, and `time_limit_cuts` in the JSON, each naming the checks that did not run and the ones that ran without their extra requests.

### Saving evidence for later checking

The JSON report keeps counts and samples, not what each page said. `--save-evidence` writes one small file per page with its title, meta tags (including `og:*` and `article:*`), headings, JSON-LD blocks as written, and main text, so a finding can be checked later without crawling again.

- `key` (default): key pages and wherever they redirected to. Without `--key-page` nothing is saved.
- `all`: every page checked. `none`: nothing.
- Folder: `<json name>-evidence/` next to `--json`, else `output/evidence/<host>/`; `--evidence-dir` chooses another. In a batch, `--save-evidence all` writes `<out>/<name>-evidence/`.
- Caps: 20,000 characters of text and 40,000 of JSON-LD per page, 500 pages and 20 MiB of page-file payloads per audit (the index is additional). What did not fit is listed in `index.json`.

The folder holds the audited site's content. Keep it under `output/`, which is git-ignored.

### Stopping and resuming an audit

With `--db-path FILE` the crawl keeps its queue and every fetched page in that file. A later run with `--resume`
continues it and reports on all pages of all sessions, not only the last one. A program that runs audits (the web
interface) can also follow an audit and stop it: `run_audit(url, config, hooks=Hooks(on_progress=..., should_stop=...))`,
see `maya_audit/progress.py`. A stop is heard between two requests. The pages already fetched are checked, the
checks that need more requests say "not assessed", and the report says the audit was stopped and can be resumed.

### Sites that build their links with JavaScript

The homepage and the key pages are also opened in the browser during the crawl. When the rendered page has clearly
more links to the site than its raw HTML, those links are followed too, and the report says that link discovery used
rendering. Only those pages are rendered for links (`render_discovery_budget`, 6 by default), so on such a site the
audit does not call a page an orphan. Turn it off with `render_discovery=False` in the configuration; it is off
whenever rendering is off.

### The JSON report format

Every JSON report starts with `schema_version` (now `1.29`). The fields are described in
[docs/REPORT-SCHEMA.md](docs/REPORT-SCHEMA.md), and the frozen shape is in `docs/report-schema-1.29.json`.
A test fails when the shape changes without a new version number, so anything built on the report can rely on it.

### Handing a report to a language model

No model is called by the audit. `crawl --llm-brief brief.json` writes the report's findings beside four prompt
templates (`maya_audit/ai_skills/`, `docs/ASSISTANT.md`) for a model you choose. Page text in the brief is fenced
as data the model must not follow, long lists inside each check are cut to their first ten items with the number
left out stated, and the brief records its own size. Check what the model wrote before relying on it:

```sh
.venv/bin/python -m maya_audit brief-check brief.json model-output.md --report reports/example.json
```

It flags claims without a known check id, numbers the audit does not contain, and anything shaped like a score. A
document with no flags passed those tests; it is not thereby correct.

### Rendering and the browser

Rendering uses Playwright's own Chromium by default. To render with a browser already installed on the machine, pass `--render-browser-channel`:

```sh
.venv/bin/python -m maya_audit crawl https://example.com/ --max-pages 50 --delay 2 --render-browser-channel chrome
```

Accepted values are Playwright channel names such as `chrome`, `chrome-beta`, `msedge` and `chromium`. A channel that is not installed does not stop the audit: INT-3 reports `raw_html_only` with the launch error, and the RND checks fall back to raw-HTML heuristics. The browser actually used is recorded in INT-3 (`browser`).

**If the browser exits with SIGTRAP on macOS**, the audit is being run from inside a sandboxed shell (for example a coding agent's command sandbox). Chromium has to register a Mach service when it starts; a sandbox that forbids this makes every Chromium-based browser abort at launch, whatever the channel. Run the audit and the test suite from a normal terminal, or allow the command to run outside the sandbox. `--render-browser-channel` does not work around it.

WebSocket connections opened by a rendered page are blocked. With Playwright older than 1.48 they cannot be intercepted; INT-3 then says "WebSocket blocking unavailable" (`websocket_blocking` in its evidence), and Chromium's disabled name resolver is what keeps the socket from connecting.

For hosted deployments, pass `--block-loopback` (or set `CrawlConfig(block_loopback=True)`) to refuse localhost targets. Per-origin audit locks coordinate processes on the same machine and lock-capable filesystem; separate hosts need a distributed lock supplied by the host application.

## The local web app

A chat-style page for running audits in the browser: a plan first, live progress, stop and resume, findings in
plain words with an action plan, comparison with the previous audit, and PDF, Markdown and JSON downloads. It runs
only on this computer.

```sh
.venv/bin/pip install -e ".[dev]"           # once
.venv/bin/python -m maya_audit_web --demo   # made-up sites and figures: nothing real is contacted or charged
.venv/bin/python -m maya_audit_web          # real audits
```

Then open http://127.0.0.1:8770. This is the one web app to use; `maya_audit_web_lite.py` (port 8765) is the older
helper, kept working but superseded.

History and saved reports are kept in `~/.maya-audit/web/`, outside this folder. Paid DataForSEO data is optional,
limited to $20 a day (shared with the command line; `MAYA_AUDIT_DATAFORSEO_DAILY_USD` changes it) and to $5 for one
audit. The plan card shows its cost before every audit, service by service, with "SERP API calls: 0" and the limits; a
plan above $2 also needs that exact amount confirmed. Reading a blocked site's content through Firecrawl is optional in the same way: a tick on
the plan card, a maximum in credits to confirm, and its own daily limit. A blocked audit's results start with one
card that explains the block and holds the Firecrawl choices. The interface is in English and Turkish (a draft, to
be reviewed by a native speaker); text the engine writes about a site stays in English.
